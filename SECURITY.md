# Security

## Reporting a vulnerability

Please do not open a public issue.

Use GitHub's [private vulnerability reporting](https://github.com/getcodescout/code_scout_flutter/security/advisories/new)
on this repository, or email **touheedkhan1408@gmail.com**.

Tell us what you found and how to reproduce it. Four things save the most time: the version of
`code_scout` you are on, the platform and Flutter version, whether you had `ProjectCredentials`
configured or were running locally with no server at all, and the smallest piece of code that shows
the problem. We will acknowledge your report within three working days and tell you whether we have
reproduced it within a week. If we ship a fix, we will credit you in the release notes unless you
would rather we did not.

## What is in scope

This SDK runs inside other people's apps, so the things worth reporting are:

- Anything that sends data the app never intended to send. CodeScout sits in the middle of an
  app's logging and its HTTP traffic, so a bug that captures more than it was asked to, or posts a
  batch anywhere other than the `link` in `ProjectCredentials`, puts a stranger's users' data on a
  server nobody chose.
- Redaction that does not redact. Whatever an app names in `RedactionBehavior` is replaced the
  moment a log is captured, before anything is written to SQLite and long before a batch is packed
  for upload, so the original should never exist on disk or on the wire. If you find a path where
  it does, that is a real bug and we want it. The network manager's in-memory pairing, a log's
  error text and a body that is not valid JSON are deliberate exceptions, covered further down.
- The project secret escaping the SDK. It should never appear in a log line, in the text of an
  exception, or in anything a crash reporter would pick up. The crash reporter is the worst of the
  three, because it hands the secret to a third party without anyone deciding to. The overlay's
  Info tab shows the secret as `set` plus its character count and never the value, and that is the
  bar every other code path has to meet.
- Anything that lets CodeScout crash or hang the host app. A debugging library that takes the app
  down with it is a serious failure, so `log()` and the shorthand methods `.v()` through `.f()`
  catch everything, and one of them throwing into your code is worth reporting. Three throws are
  deliberate and are not bugs. `logMessage()` rethrows, which is the whole reason to await it
  instead of calling `log()`. `ProjectCredentials` throws from its constructor when the id, the
  secret or the link is malformed, so a link like `localhost:24275/` fails at startup where you can
  see it rather than quietly at the first upload. And `init()` throws if it is called a second
  time.
- The database browser showing anything the app never registered, editing anything registered
  without `writable: true`, or accepting anything from the dashboard that amounts to a SQL
  statement. The rules that feature lives by are below.
- A pairing code that gets a device into another project's session, works twice, or works after it
  expired.

## What leaves the device

Every launch records the device model, the OS name and version, your app's version and build
number, the SDK's own version, and a random installation id. The id is generated by the SDK on
first launch and stored in its own database, so it identifies the install to nobody else and
uninstalling the app destroys it. `captureDeviceInfo` and `captureAppContext` both default to true;
set either to false to opt that group out. No user identity is collected unless the app calls
`setUser()`.

All of it goes to the `link` in `ProjectCredentials` over `dart:io`'s `HttpClient`, with exactly
the transport security that URL names. An `https://` link gets the platform's normal certificate
validation and nothing more: the SDK does not pin certificates and does not touch
`badCertificateCallback`, so a self-signed development certificate is rejected rather than quietly
trusted. An `http://` link is accepted, and over it the `X-Project-Secret` header and every log in
every batch cross the network in cleartext. That is fine for an emulator talking to a dashboard on
the same machine and wrong for anything else. Android refuses cleartext HTTP by default, which is
the platform agreeing.

## The overlay is on in release builds

`init()` puts the floating button on screen whenever it can get a `BuildContext`. There is no
build-mode check anywhere in the overlay; the only `kReleaseMode` check in the SDK is the one that
ignores database registration. So unless you act, anyone holding a production phone can tap the
button and read the last 500 logs of the current launch from an in-memory buffer, the Network tab's
headers and bodies as captured, and the host the app reports to.

What they cannot read is the credential. The Info tab prints the project id abbreviated and the
secret as `set` plus its character count, never the value, precisely because that screen gets
screenshotted into bug reports.

For a shipped app, call `CodeScout.instance.hideIcon()` right after `init()`, or only initialise
CodeScout in debug builds. The buffer is memory only and dies with the process either way.

## The database browser

While a device is paired into a live session, the dashboard can browse local storage the app has
offered up: SQLite through `CodeScoutSqflite`, and anything with keys and values through
`CodeScoutKeyValue`. It is the feature with the biggest blast radius in the package, and these are
the rules that hold it together:

- Nothing is browsable until the app calls `registerDatabase`. There is no scanning for `*.db`
  files, so what an app exposes can be read from its own source code.
- Registration is ignored in release builds unless the call passes `allowInRelease: true`. The
  default is what almost everybody should ship.
- Nothing is editable unless the registration said `writable: true`. The flag is enforced in the
  registry every op goes through, not in the dashboard's UI, so no op can route around it. The
  dashboard's write route also requires project-manage rights server-side, so a write is behind
  two gates.
- The dashboard never sends SQL. The protocol is five ops (`sources`, `namespaces`, `schema`,
  `rows`, `update`) and none of them has a field a statement could go in. The device builds every
  query from its own schema. Read-only is a property of what the protocol can express, not a rule
  anyone has to remember to enforce.
- Columns and keys whose names match your `RedactionBehavior.bodyKeys` never leave the device, and
  they cannot be written either, because an edit carries the value the dashboard was shown to
  catch conflicts, and a value nobody was shown cannot be compared against anything.
- Every successful edit logs itself at `system` level, exempt from level filtering and sampling,
  so the change sits in the session's timeline with who made it.
- Nothing browsed is stored on the server. Rows go from the phone to the dashboard's browser tab
  and nowhere else.

## Live sessions

A live session streams one device's logs to the dashboard in real time. The pairing code decides
which session a device joins, never whether it may connect: the device's WebSocket carries the
same project id and secret as an upload, and the server checks them before it reads a pairing
frame. The code itself is minted by someone signed in to the dashboard with access to the project.
It is six characters from an alphabet with no 0/O, 1/I/L, 5/S or 8/B, drawn from `crypto/rand`,
single use, dead after five minutes, and bound to the project that minted it. Anyone holding the
phone can type a code into the overlay's Live tab, but without a dashboard login on the other end
there is no code to type.

While paired, every log streams above the sampling gate, because somebody who deliberately paired
with a device should see everything it does. Network calls carry their headers and bodies on the
live wire as captured, which means already redacted. A hand-written log's metadata does not travel
at all, because nothing on the live logs pane reads it. Nothing streamed is persisted, on the
server or anywhere else.

## Things that are deliberate, and are not bugs

**Nothing is redacted unless the app asks for it.** Out of the box the SDK records what your app
sent, including headers. That is a product decision, not an oversight: the auth header is often
exactly why a request is failing. Use `RedactionBehavior.recommended()` to turn on the usual
suspects in one line. The one thing the default does change is size: a request or response body
over 32 KB is cut to 32 KB with a note saying how big it really was, because uploading megabytes
off somebody's phone spends data they never agreed to spend. That is a size limit rather than a
privacy setting, and `maxBodyBytes: 0` turns it off.

**Redaction covers what is stored and uploaded, not every surface a value crosses.** A named value
is replaced on the log entry as it is captured, so the console printer and the overlay, its copy
buttons included, show `[redacted]` too. One path keeps the real value on the device on purpose:
the network manager holds the original request in memory for up to two minutes while it waits for
the matching response. It writes nothing to disk and uploads nothing, which is why it is not a bug.
Redaction finds values by name in headers, JSON bodies and metadata, so two things that are stored
and uploaded are outside it.

**The error you log is not redacted.** What is stored is the error's `toString()`, and some
exceptions quote what they failed on. A `FormatException` from `jsonDecode` quotes the part of the
body where parsing stopped, so a value named in `bodyKeys` can reach a log's error text, which is
stored and uploaded as it is. If the body can hold one, log the exception's `message` rather than
the exception.

**A body that is not valid JSON is not scanned.** Body keys are found by reading the body as JSON.
A broken body, or the form-encoded string `package:http` sends for a `Map` body, has no keys to
match, so nothing in it is redacted. A form body's `password=...` is stored and uploaded as sent,
even under `RedactionBehavior.recommended()`.

**Logs are stored unencrypted in the app's own SQLite database.** They live in your app's private
storage, protected by the same OS sandbox as the rest of your app data, in `code_scout.db`, opened
in WAL mode, so recent writes also sit in the `-wal` file beside it. A row stays until the server
accepts the batch that carries it, and is deleted then. With no `ProjectCredentials` configured,
which is the supported local-only mode, nothing is ever uploaded, so nothing is ever deleted and
the database grows for the life of the install; there is no local size cap or age limit. During an
upload the batch also exists briefly as a tar.gz in the app's temporary directory, deleted whether
the upload landed or not. If your threat model includes a rooted or jailbroken device, do not log
secrets.

**The project secret ships inside the app binary.** Anyone who can read your app can read it. It
authorises three things against one project and nothing else: uploading logs, asking the server
whether the credentials are good (the answer carries the project's name and sampling rate), and
opening the device socket for a live session. It cannot read a log back, it cannot see any other
project, and it is not a dashboard account. Watching a device also needs a pairing code minted by
somebody signed in to the dashboard, so the secret alone never lets anyone see anything. If it
leaks, rotate it in the project's settings, and know what rotating does: there is one live secret
per project, so every build already on a phone starts failing authentication at its next upload.
The SDK treats that as an ordinary failure, pauses and retries rather than giving up, so those
logs wait on the device instead of being lost, but they will not arrive until an update ships the
new secret. Rotation belongs next to a release, not on its own.

## Supported versions

Security fixes land on `main` and ship in the next release of the newest line. There are no
maintenance branches and no backports, so the way to get a fix is to upgrade.

One past defect is a concrete reason to upgrade: through 1.4.0, `printToConsole` was declared and
never read, so every release build printed every log to the platform console no matter what the
app configured. On Android that is logcat, readable by anyone who can attach `adb` to the device.
It is honoured from 1.5.0 and defaults to printing in debug builds only.

## If you are shipping this to production

Decide about redaction before you ship, not after. Read
[the redaction guide](https://codescout.tech/docs/guides/redaction/), and consider
`RedactionBehavior.recommended()` as a starting point rather than a finished answer, since only you
know what your app puts in its own log lines.

Decide about the overlay in the same breath: hide it with `hideIcon()`, or initialise CodeScout
only in debug builds. Point `link` at an `https://` URL. And leave `writable: true` and
`allowInRelease` out of any `registerDatabase` call that ships; the defaults are the safe ones.
